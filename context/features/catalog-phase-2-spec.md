# Frontend API Integration Layer Phase 2 Spec

## Overview

This is phase 2 of 6 for api layer in frontend part.

## Overview

Create a clean frontend integration layer responsible for communicating with the existing PHP backend API.

The frontend must stop relying on mock product data for CRUD operations and instead use the real backend endpoints.

The goal is to keep:

- UI components focused on presentation and interaction
- API communication isolated in a dedicated layer
- TypeScript types explicit and reusable
- Backend response handling consistent
- Error handling centralized where practical
- Product-specific API logic easy to test and maintain

Do not place raw `fetch()` calls directly inside product UI components unless there is a strong reason.

---

## Backend API Contract

The existing backend exposes these routes:

```text
GET    /api/products
GET    /api/products/{id}
POST   /api/products
PUT    /api/products/{id}
DELETE /api/products/{id}
```

Use relative URLs only:

```ts
fetch("/api/products");
```

Do not hardcode:

```text
http://localhost:8080
```

Nginx already handles routing `/api/*` requests to the PHP backend.

---

## Product API Shape

The backend returns products in this shape:

```ts
type Product = {
  id: number;
  name: string;
  price: number;
  currency: string;
};
```

Example backend response:

```json
{
  "id": 1,
  "name": "Keyboard",
  "price": 9990,
  "currency": "EUR"
}
```

`price` is stored and returned in minor units.

Example:

```text
9990 = €99.90
```

Do not convert the API contract to floating-point monetary values.

Only format the value for display in the UI.

## Product Input Type

Example:

```ts
export type ProductInput = {
  name: string;
  price: number;

```

Do not reuse a full `Product` type for create requests because `id` is generated by the backend.

## TypeScript Rules

Use TypeScript strictly.

Prefer:

```ts
Product;
ProductInput;
Promise<Product>;
Promise<Product[]>;
Promise<void>;
```

Avoid:

```ts
any
unknown without narrowing
untyped JSON responses
duplicated object shapes
```

If `unknown` is used for error handling, narrow it safely.

Example:

```ts
if (error instanceof Error) {
  setError(error.message);
}
```

Do not cast arbitrary API responses to `Product` without a clear reason.

## Generic HTTP Helper

Create:

```text
frontend/src/api/http.ts
```

Purpose:

- Handle JSON responses
- Handle HTTP errors
- Handle `204 No Content`
- Keep repeated response logic out of each API function

Suggested design:

```ts
export class ApiError extends Error {
  constructor(
    message: string,
    public readonly status: number,
  ) {
    super(message);
    this.name = "ApiError";
  }
}
```

Create a helper like:

```ts
export async function handleResponse<T>(response: Response): Promise<T> {
  if (!response.ok) {
    let message = "Something went wrong";

    try {
      const body = await response.json();

      if (
        typeof body === "object" &&
        body !== null &&
        "error" in body &&
        typeof body.error === "string"
      ) {
        message = body.error;
      }
    } catch {
      // Keep fallback message.
    }

    throw new ApiError(message, response.status);
  }

  if (response.status === 204) {
    return undefined as T;
  }

  return response.json() as Promise<T>;
}
```

Keep this helper generic.

Do not add Product-specific behavior to `http.ts`.

## Create Product

Implement:

```ts
export async function createProduct(input: ProductInput): Promise<Product> {
  const response = await fetch(endpoint, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
    },
    body: JSON.stringify(input),
  });

  return handleResponse<Product>(response);
}
```

Expected request:

```json
{
  "name": "Keyboard",
  "price": 9990,
  "currency": "EUR"
}
```

Expected status:

```text
201 Created
```

## Catalog Page Integration

Update the existing catalog page to use the API layer.

Do not call `fetch()` directly from `CatalogPage.tsx`.

Import:

```ts
import {
  createProduct,
  deleteProduct,
  getProducts,
  updateProduct,
} from "@/api/products";
```

The page should own page-level state.

Recommended state:

```ts
const [products, setProducts] = useState<Product[]>([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState<string | null>(null);
const [selectedProduct, setSelectedProduct] = useState<Product | null>(null);
const [submitting, setSubmitting] = useState(false);
```

Keep dialog state separate from data state.

---

## Initial Product Loading

On page mount:

```ts
useEffect(() => {
  void loadProducts();
}, []);
```

Implement:

```ts
async function loadProducts() {
  try {
    setLoading(true);
    setError(null);

    const data = await getProducts();

    setProducts(data);
  } catch (error) {
    setError(
      error instanceof Error ? error.message : "Could not load products",
    );
  } finally {
    setLoading(false);
  }
}
```

Do not use mock data after this integration is complete.

## Create Product Flow

When the user submits the Add Product form:

```text
ProductForm
   |
   v
createProduct(input)
   |
   v
POST /api/products
   |
   v
PHP backend
   |
   v
Product returned
   |
   v
update local state
```

Recommended behavior:

```ts
const created = await createProduct(input);

setProducts((current) => [created, ...current]);
```

Then:

- Close the dialog
- Reset form state
- Clear previous errors

Do not reload the entire browser page.

---

## Update Product Flow

When the user saves edits:

```ts
const updated = await updateProduct(product.id, input);
```

Then:

```ts
setProducts((current) =>
  current.map((product) => (product.id === updated.id ? updated : product)),
);
```

Then close the dialog.

Do not refetch the entire product list unless needed.

---

## Delete Product Flow

After confirmation:

```ts
await deleteProduct(id);
```

Then:

```ts
setProducts((current) => current.filter((product) => product.id !== id));
```

Keep destructive confirmation in the UI.

## Price Conversion

The API expects price in minor units.

If the form displays:

```text
99.90
```

convert it before calling the API:

```ts
const priceInMinorUnits = Math.round(Number(price) * 100);
```

Send:

```json
{
  "price": 9990
}
```

For display, convert back:

```ts
export function formatMoney(amount: number, currency: string): string {
  return new Intl.NumberFormat("en", {
    style: "currency",
    currency,
  }).format(amount / 100);
}
```

Do not store formatted strings in Product state.

Keep state in the API/domain representation.

## Error Handling

Backend errors may look like:

```json
{
  "error": "Product name cannot be empty."
}
```

The frontend should display the backend message.

Do not replace useful backend messages with generic text unnecessarily.

Use `ApiError` when useful:

```ts
try {
  await createProduct(input);
} catch (error) {
  if (error instanceof ApiError) {
    setError(error.message);
  }
}
```

Keep error handling readable.

## Loading and Submitting States

Initial product load:

```text
loading = true
```

Form submission:

```text
submitting = true
```

These are different states.

Do not reuse one global `loading` flag for every operation.

For example:

```ts
const [loading, setLoading] = useState(true);
const [submitting, setSubmitting] = useState(false);
```

Disable submit buttons while submitting.

## Backend Remains Authoritative

Frontend validation is for UX only.

The PHP Domain remains the source of truth for business rules.

For example:

```text
Frontend:
price >= 0
    -> immediate UX feedback

Backend Domain:
Money rejects negative amount
    -> authoritative rule
```

Do not duplicate complex business logic in React.

---

## Scope

Implement only the frontend API integration layer and connect the existing Product UI to it.

Do not:

- Redesign the backend
- Change backend routes
- Change Product JSON field names
- Replace React Router
- Replace Tailwind or shadcn
- Introduce a new state library
- Rebuild the Product UI from scratch unless required for API integration

Preserve the existing `/catalog` page and current visual design.

---

## Definition of Done

This phase is complete when:

- `/catalog` loads products from `GET /api/products`
- Mock product data is no longer used as the active source
- Add Product calls `POST /api/products`
- Edit Product calls `PUT /api/products/{id}`
- Delete Product calls `DELETE /api/products/{id}`
- Product state updates without a full browser reload
- Backend errors are visible in the frontend
- Loading and submitting states work correctly
- API calls are isolated in `src/api`
- Product types are isolated in `src/types`
- No `any` is introduced
- Existing Tailwind/shadcn UI remains intact
- Existing React Router `/catalog` route remains intact
- TypeScript build succeeds
